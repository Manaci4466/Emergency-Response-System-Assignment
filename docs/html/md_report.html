Approach & implementation

The system turns noisy road reports and historical traffic observations into expected travel times, finds routes with A*, and assigns responders with a constraint solver each time new incidents become known. run.py writes plan.json and statistics.txt and then checks the plan with an independent validator. Roads are directed: A→B and B→A never share reports or observations.

Bayesian road model (bayes.py, Notes 6). Each road has its own Bayesian network Weather → Status → {Citizen, Police, Sensor}, solved by enumeration: P(S | w, r) ∝ P(S|w)·Π P(rᵢ|S). The reports may be multiplied because Status is their only parent (conditionally independent given S); P(w) is the same for every status and cancels in the normalisation. For roads without reports the weather is summed out, giving the prior Open 0.685 / Congested 0.18 / Blocked 0.135. Example: small N1→N2 (Rain; Blocked, Blocked, Congested) gets P(Blocked) = 0.527 ≥ τ, so it is avoided, while N2→N1 (all Congested) stays usable.

HMM traffic model (hmm.py, Notes 8). Hidden state = true traffic level, evidence = observed level. The forward algorithm alternates time elapse and observation and normalises every step, which prevents numerical underflow. We filter instead of running Viterbi because planning needs the distribution of the current level, not the most likely history. The traffic at t = 0 is the filtered belief plus one prediction step, converted into an expected multiplier (Low 1.0, Medium 1.25, High 1.5; roads without observations ×1.0).

**Cost model and A*** (cost_model.py, search.py, Notes 1). Expected time = distance/speed × status multiplier (P(O)·1 + P(C)·1.5)/(P(O)+P(C)) × traffic multiplier; a road is unusable if P(Blocked) ≥ τ = 0.5. A* (graph search, closed set) uses h = straight-line distance / fastest road speed: admissible because every road is at least as long as the straight line and every multiplier is ≥ 1, and consistent by the triangle inequality, so the closed set never discards a better path. The program checks the first condition on each scenario and otherwise uses h = 0 (uniform-cost search).

CSP allocation (allocation.py, Notes 2). Each round (the incidents with the same timestamp) is a CSP: variables = incidents, domains = capable responders that can reach them. A busy responder is queued and starts its next job from its last incident once that job ends. Deadlines are soft (late help beats no help), so forward checking is adapted: an incident with no on-time responder left does not fail the branch, it adds its priority weight (Critical 8, High 4, Medium 2, Low 1) to a lower bound. Branch and bound minimises first the priority-weighted lateness and then the total response time. MRV picks the incident with the fewest on-time responders. Because the assignment order also fixes the job order of a shared responder, MRV here changes the answer, not only the speed: without it, R10 in medium handles I2 before the Critical I3, which then arrives late. The bound is valid only because A* returns true shortest paths: admissible h → optimal paths → valid bound → correct branch and bound. Rounds are solved in time order with only the incidents known at that moment (no clairvoyance) and committed immediately.

Testing & results

python -m pytest runs 110 tests (plus an opt-in, slow mutation sweep), using hand-calculated values (N1→N2 posterior 0.014 / 0.459 / 0.527; the classic umbrella HMM exactly with fractions, 2/5 and 15/128; the allocation of small's first round), differential testing (A*, UCS and an independent Floyd–Warshall agree on every node pair; the CSP matches exhaustive brute force on the first round of every scenario) and property tests (consistent heuristic, no clairvoyance). The validator reads only plan.json and the raw files and never imports the planner; all 13 injected plan faults are caught with exactly the expected error. A mutation sweep applies 35 typical bugs from every module to a copy of the project: 35 of 35 are caught (its first run exposed an untested τ boundary). Testing works in layers: the validator shares the cost model, so an error in the model itself (e.g. Congested ×1.0 instead of ×1.5) still produces "valid" plans; only the hand-calculated unit tests catch that. In the results below, deadlines met = on-time arrivals / all incidents (unhandled = missed), the average response time (arrival − timestamp) is over handled incidents, and weighted missed = Σ priority weights of late or unhandled incidents. All values are expected seconds under the model, not observed ground truth.

The results depend more on the modelling assumptions than on the algorithm: medium falls from 91.7% to 33.3% when its unobserved roads get the stationary traffic multiplier, because some of its deadlines are only 20 s after the incident appears. Monte Carlo sampling (prior sampling, Notes 6) draws 5000 possible worlds, sampling each road's true status and traffic level from our beliefs, and replays the fixed plan in each. Raising τ to 0.6 doubles small's planned deadlines met, but the sampled value drops slightly (36.2% → 35.1%), because the extra roads are blocked in 52.7% of the worlds; this supports τ = 0.5. R1's route to the Critical I2 crosses two unreported roads and is blocked in 24.9% of the worlds (analytically 1 − 0.865² = 25.2%).

Critical reflection

Limitations. These limitations became clear during different phases of the project. Every number in this report is an expected value under my own model. A "valid" plan only respects the hard constraints under my beliefs: the Monte Carlo replay shows that at least one planned route is blocked in 64–97% of the sampled worlds, and that the route to a Critical incident in small is blocked in one world out of four. The beliefs are computed once at t = 0 and used for the whole simulation, assignments are never re-planned when a more urgent incident arrives, reports are assumed independent given the road status (false if citizens copy the police), and the multipliers are chosen by me, not learned from data. The experiments show that these assumptions move the results more than the choice of algorithm.

The LLMs. They made me much faster and explained the theory well, and the reviewer–implementer setup found edge cases I would have missed. They also misled me in convincing ways: a test that could never fail, a wrong eigenvalue, a commit made while tests were failing, one scenario's stationary multiplier applied to all three scenarios, and two wrong predictions from the reviewing LLM. I caught each one only because I treated every claim as something to test: hand calculations, independent scripts and mutation testing. The main lesson is that a passing test is only evidence if it can fail.

Next steps (suggested by Claude Code; I adopted them after checking their reasoning). (1) Rolling-horizon re-planning: re-solve when a new incident arrives and compare the weighted missed and the Monte Carlo deadlines met on all three scenarios. (2) Risk-aware routing that penalises P(Blocked) instead of a hard τ, measured by the Monte Carlo P(route blocked) and deadlines met. (3) Time-varying traffic, which needs a time unit for the observations, measured the same way.
